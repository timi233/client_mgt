## 1. Codex 技术审查反馈

### 1.1 技术可行性分析
- **技术栈**：Django + DRF + PostgreSQL 适合典型CRM的事务性、关系型数据和权限隔离；配合 Next.js 14 可行。关键在于多租户隔离策略与权限模型落地。
- **数据模型**（10核心实体）：整体覆盖主流程，但多租户/唯一性约束存在风险（`feishu_open_id`/`partner_code`/`work_order_no`/`order_no`/`unified_social_credit_code` 需明确是否“全局唯一”还是“租户内唯一”）。多处 JSONField（tags/attachments/sync_status）查询与约束能力有限，后期统计、 过滤会受限。
- **系统集成架构**：REST + MQ + Celery 组合可行，但需要清晰的主从系统边界、幂等键、重试/补偿机制和 outbox 模式，否则容易出现重复/丢失事件。

### 1.2 潜在优化空间
- **数据库设计优化**：统一加 `account` 外键到所有顶层实体（Lead/Opportunity/Activity/ChannelPartner/WorkOrder/Order 等）并建立 `account+关键字段` 复合索引；将高频过滤字段转为枚举或独立维表；JSON 标签/附件考虑改为数组或关联表以支持查询和约束；软删除字段需配合部分唯一索引避免“删后 无法新建”。
- **API 设计改进**：全量/增量接口与版本控制（`/api/v1`）；支持幂等键（Idempotency-Key）；分页、 排序、过滤、搜索规范；事件推送与查询解耦（推送只传事件ID，详细数据由拉取接口获取）。
- **性能优化考虑**：LTV 计算采用增量更新（基于商机/订单变化触发），大屏/报表使用缓存或物化视图；列表页注意 `select_related/prefetch_related`；MQ 失败重试和死信队列。

### 1.3 架构关注点
- **多租户实现细节**：建议在中间件统一注入 `account_id`，所有查询强制带过滤；模型唯一约束/索引以 `account_id` 为前缀；后台管理与异步任务也需强制租户上下文。
- **飞书集成挑战**：tenant 级 App 凭证管理、组织架构同步差异（部门合并/人员停用）、ID 映射与历史兼容、API 速率与重试。
- **消息队列使用场景**：事件发布需配合 outbox 表确保“写库+发消息”一致性；消费者幂等；提供重试/死信/人工补偿机制。
- **LTV评分系统复杂度**：多来源数据融合、定时批处理+实时触发容易相互覆盖；需要明确“评分版本”和“ 计算时间点”，否则前端展示不一致。

## 2. Gemini 业务逻辑审查反馈

### 2.1 业务需求完整性 (Business Requirement Completeness)

*   **业务流程清晰度**：
    *   **核心流程覆盖**：文档清晰定义了从线索(Lead)到客户(Customer)再到商机(Opportunity)的 转化流程，以及后续的订单(Order)和派工(Work Order)流转。
    *   **LTV 闭环**：LTV（客户生命周期价值）不仅仅是一个计算公式，还设计了其在销售策略、预 警和报表中的应用，形成了业务闭环。
    *   **缺口**：**公海池(High Seas)机制**未明确提及。虽然有 `owner` 字段，但缺乏关于客户回收、领取、分配的具体规则描述，这对于 B2B 销售团队至关重要。

*   **用户角色与权限**：
    *   **角色定义**：定义了销售、经理、高层、售前/售后等角色，覆盖面较全。
    *   **权限细节缺失**：缺乏具体的**数据访问权限矩阵**。例如：销售经理是否可以查看非下属团队的客户？售前支持人员对商机的编辑权限范围是什么？字段级的敏感数据（如LTV评分、渠道佣金比例 ）对不同角色的可见性未细化。

*   **业务场景覆盖**：
    *   涵盖了 B2B 销售的长周期特点（阶段历史记录）。
    *   **渠道管理**和**派工管理**的集成扩展了传统 CRM 的边界，增强了业务完整性。

### 2.2 文档质量评估 (Document Quality Assessment)

*   **描述清晰度**：
    *   数据模型（Model）定义非常详细，字段类型和用途标注清晰，易于开发理解。
    *   集成架构图和 API 示例具体且具有可操作性。

*   **潜在矛盾与冲突**：
    *   **Lead 与 Customer 状态的重叠**：`Lead` 模型代表线索，但 `Customer` 模型中又有一个 `status='lead'` (线索)。这可能导致业务逻辑混淆：什么时候用 `Lead` 表，什么时候用 `Customer`  表？通常建议明确界定（例如：未确认意向为 Lead 表，确认后转入 Customer 表）。
    *   **硬编码年份**：LTV 数据模型中直接定义了 `revenue_2022_wan`、`revenue_2023_wan` 等字段。这不具备可持续性，2026年以后系统将无法扩展。

*   **缺失的业务细节**：
    *   **线索转化逻辑 (Conversion Mapping)**：从 `Lead` 转化到 `Customer` + `Contact` + `Opportunity` 时，具体字段如何映射？是否自动创建商机？
    *   **数据迁移策略**：虽然提到"从空数据开始"，但对于存量客户如何初始化 LTV 数据（特别是 历史交易数据）缺乏具体方案。

### 2.3 业务逻辑问题 (Business Logic Issues)

*   **LTV 评分模型的合理性**：
    *   **风险**：LTV 计算依赖大量手动录入的非结构化数据（如"行业地位"、"IT投入"）。如果销售录入随意，LTV 分数将失去参考价值。
    *   **建议**：需要增加数据录入的验证机制或引入第三方数据源自动填充（如工商数据接口）。
    *   **模型僵化**：当前 LTV 权重和阈值（如 "Top 500" +15分）是硬编码的。业务规则变化时， 系统调整成本高。建议将评分规则配置化。

*   **销售机会管道 (Pipeline)**：
    *   目前的 `Opportunity` 模型中，`probability` (成交概率) 似乎是手动填写的。通常建议与 `stage` (销售阶段) 挂钩（例如：方案阶段固定为 50%），允许手动微调，以保证预测的一致性。

*   **系统集成逻辑**：
    *   **数据一致性**：在“订单系统”集成部分，`Opportunity` 的 `actual_amount` 与 `Order` 的 `order_amount` 存在数据冗余。需明确以哪个为准，以及发生变更时的同步方向。

## 3. 待澄清问题汇总

### 3.1 技术类问题 (Codex)
1.  **多租户隔离**：是“单库单表+account_id”还是“schema/DB per tenant”？是否需要数据库级 RLS？
2.  **唯一性约束**：飞书用户标识 (`open_id`/`union_id`/`user_id`)、统一社会信用代码、订单号等是否应当租户内唯一还是全局唯一？如何处理跨租户同一人？
3.  **LTV 公式冲突**：前文“潜力评分+实际价值(金额)”与后文“最终评分仅基于评分项”不一致，最终对外展示的是分数还是金额？
4.  **历史数据初始化**：LTV 依赖的历史数据来源（订单/商机）在“从空数据开始”下如何初始化？
5.  **系统集成主从**：客户主数据以 CRM 为准，但渠道/派工/订单系统是否也可写回？冲突优先级和审批流程是什么？
6.  **消息队列选型**：选择 RabbitMQ 还是 Kafka？如果使用 Kafka，Celery 消费者如何适配？
7.  **飞书集成范围**：仅登录+组织同步，还是还需审批/消息通知/机器人？token 刷新、速率限制、离线访问策略？

### 3.2 业务类问题 (Gemini)
1.  **Lead 生命周期**：`Lead` 表中的数据在转化后是保留、删除还是归档？如果客户再次产生新线索，是新建 `Lead` 记录还是在现有 `Customer` 上新增商机？
2.  **LTV 字段可持续性**：`Customer` 表中的 `revenue_202x_wan` 字段如何处理跨年问题？建议改为子表结构。
3.  **飞书集成深度**：本地部署环境如何与飞书云端进行组织架构同步？是否需要内网穿透或特定的安全网关配置？
4.  **公海池规则**：销售长期未跟进的客户是否会自动退回公海？规则是什么（如：30天无 Activity）？
5.  **LTV 数据录入质量**：大量依赖手动录入的非结构化数据（如"行业地位"）如何保证准确性？
