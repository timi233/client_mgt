# CRM系统技术决策 - 最终方案

## 背景

本文档结合Codex和Gemini的推荐意见，为CRM系统的7个关键设计问题制定最终技术决策，旨在平衡功能性、可维护性和扩展性。

## 决策摘要

采用单数据库tenant_id隔离 + 组合唯一约束 + RFM模型LTV评分 + 渐进式数据导入 + CRM为主数据源 + RabbitMQ+Celery异步处理 + 核心飞书集成的整体方案。架构在中等规模下平衡复杂度和功能需求，具备良好扩展性。

---

## 决策细节

### 1. 多租户隔离策略

**决策**: 采用方案A - 单数据库 + account_id字段隔离，**PostgreSQL RLS作为可选增强层**

**理由**:
- 中等规模CRM（<100租户）方案A维护成本最低
- 跨租户查询灵活，数据迁移简单
- 配合Django middleware自动过滤tenant数据
- 部分索引优化查询性能

**权衡**:
- 需应用层严格过滤，存在租户间数据泄露风险
- 需完善的审计和权限控制机制
- 方案B（schema隔离）适合强隔离需求但运维复杂
- 方案C（独立DB）成本高，仅适合大型企业客户

**Gemini RLS建议**: Gemini建议启用PostgreSQL Row Level Security作为数据库层面的强制隔离保护。**最终决策**: RLS作为生产环境可选增强，初期先通过应用层控制，数据量大或安全要求高时可逐步启用。

**关键行动**:
- [ ] 创建Tenant模型，所有业务表添加tenant_id外键
- [ ] 实现TenantMiddleware自动注入tenant_id到查询上下文
- [ ] 为tenant_id字段创建部分索引: `CREATE INDEX idx_table_tenant ON table(tenant_id) WHERE deleted_at IS NULL`
- [ ] 编写审计日志记录跨租户访问尝试
- [ ] 准备RLS迁移脚本（可选启用）

### 2. 唯一性约束范围

**决策**: Feishu用户ID和飞书组织ID全局唯一；订单号/信用代码采用 tenant_id + code 组合唯一

**理由**:
- 飞书ID是平台级标识，天然全局唯一
- 订单号、信用代码在同一租户内唯一即可，避免跨租户冲突
- 同一用户多租户场景通过UserTenant关联表支持

**权衡**:
- 组合唯一索引需包含tenant_id，查询时需额外过滤条件
- 全局唯一字段直接UNIQUE约束，组合唯一用UniqueConstraint
- PostgreSQL中多个NULL值可共存，需注意业务逻辑处理

**关键行动**:
- [ ] FeishuUserId字段添加UNIQUE约束
- [ ] Order/CompanyCreditCode添加UniqueConstraint(tenant_id, code)
- [ ] 创建UserTenant关联表支持用户多租户
- [ ] 数据导入时检查唯一性约束冲突处理逻辑

### 3. LTV（客户生命周期价值）公式

**决策**: 采用4层模型架构 + 双轨输出模型

**4层模型架构**:
1. **Customer**（基础信息 + LTV缓存）: 存储客户基础信息，LTV缓存字段（ltv_score、ltv_tier、ltv_calculated_at）用于快速查询
2. **CustomerLTVProfile**（LTV输入特征）: 存储LTV计算所需的输入特征，支持多版本算法（profile_version字段）
3. **CustomerLTV**（LTV结果 + 历史追踪）: 存储LTV计算结果（评分、分层、实际营收追踪）
4. **LTVHistory**（变化历史）: 记录LTV变化快照，用于趋势分析

**双轨输出**:
- **LTV_score** (0-100): 存储在CustomerLTV.ltv_score，综合评分用于客户分层
- **LTV_amount**: 存储在CustomerLTV，公式为 `historical_revenue + predicted_revenue + current_pipeline_value`

**计算公式**:
- **Score公式**: `(显性价值 × 0.4) + (隐性价值 × 0.4) + (增长价值 × 0.2)`
- **Amount公式**: `历史成交金额 + 当前管道价值 + 预测营收`

**架构优势**:
- 支持算法迭代和A/B测试：通过profile_version字段支持多版本算法并存
- 降低迁移风险：模型调整时独立LTVProfile表，不影响Customer基础功能
- 未来可独立为微服务：LTV计算逻辑可独立部署，提升计算能力

**理由**:
- 评分系统基于现有前端逻辑（潜力评分），结合显性/隐性/增长价值维度
- 金额模型追踪实际营收、管道价值和预测值，全面反映客户价值
- 双轨模型支持不同业务场景：筛选用score，排序用amount

**权衡**:
- 复杂公式增加计算成本，需定时任务异步更新
- 4层架构增加数据关联复杂度，需确保同步一致性
- 冷启动时数据不足，可用简化版公式

**关键行动**:
- [ ] 实现4层模型（Customer、CustomerLTVProfile、CustomerLTV、LTVHistory）
- [ ] 实现LTV计算Celery任务：读取CustomerLTVProfile → 计算score和amount → 更新CustomerLTV
- [ ] 配置Celery Beat每日定时更新LTV
- [ ] 创建LTVHistory快照：每次LTV更新时记录历史
- [ ] 为LTV字段添加索引：Customer.ltv_score、CustomerLTV.ltv_score、CustomerLTV.historical_revenue

### 4. 历史数据初始化

**决策**: 冷启动阶段设计标准化导入模板 + 数据清洗工具 + 渐进式导入策略 + 启发式评分

**理由**:
- 标准模板确保数据格式一致
- 渐进式导入便于问题定位和回滚
- 无历史数据客户采用启发式评分（行业基准+首次订单金额）

**权衡**:
- 全量导入风险高，先导入1-2个租户试运行
- 数据清洗耗时但保证质量
- 启发式评分可能不准确，随交易数据积累逐步修正

**关键行动**:
- [ ] 设计Excel/CSV导入模板（包含必填字段、数据校验规则）
- [ ] 开发Django management command: `python manage.py import_crm_data --batch-size=500`
- [ ] 实现数据校验 → 重复检测 → Feishu ID映射 → 创建记录流程
- [ ] 编写启发式评分算法: `initial_score = base_industry_score + log(first_order_amount) * weight`
- [ ] 导入过程记录日志，失败数据单独导出便于修正

### 5. 系统集成主从关系

**决策**: CRM为主数据源，飞书为只读同步目标；审批场景CRM回写飞书审批状态

**理由**:
- CRM作为业务核心系统，客户数据、订单数据应以此为准
- 飞书通过webhook接收CRM数据变更通知并同步
- 双向同步冲突少，通过状态机确保一致性

**冲突解决规则**:
- 优先级: 人工手动修改 > 系统自动同步 > 初始导入
- 同一字段冲突: 飞书侧联系人手机号等采用last-write-wins（时间戳判断）
- 审批状态: CRM为准，飞书仅显示

**权衡**:
- 需增加时间戳和来源字段审计变更
- 实时同步延迟可能短暂影响用户体验
- 考虑增加同步状态提示

**关键行动**:
- [ ] 所有模型添加 `updated_at` 和 `source` 字段
- [ ] 实现同步任务队列: 飞书webhook → Celery task → 更新CRM
- [ ] 冲突检测逻辑: `if source == 'feishu' and feishu_timestamp > crm_timestamp: update()`
- [ ] 审批流程: CRM提交 → 飞书创建审批 → 飞书回调更新CRM订单状态
- [ ] 同步状态枚举: `synced, syncing, pending, failed`

### 6. 消息队列选择

**决策**: RabbitMQ + Celery

**理由**:
- CRM场景消息量中等（日处理<10万条），RabbitMQ管理简单、性能足够
- Django生态成熟，Celery支持完善
- 支持定时任务、重试、任务链，满足异步处理需求
- Kafka适合海量日志或流处理，对CRM过度设计

**权衡**:
- RabbitMQ需单独维护，增加运维成本
- Celery任务失败需处理（监控+告警+重试队列）
- 轻量场景可用Django内置队列，但不适合生产环境

**关键行动**:
- [ ] 安装配置RabbitMQ和Celery
- [ ] 定义异步任务: 同步飞书数据、计算LTV、发送通知
- [ ] 配置Celery Beat定时任务（每日LTV更新、token刷新）
- [ ] 实现任务失败告警（Sentry/钉钉通知）
- [ ] 配置任务重试策略: `autoretry_for=(Exception,), max_retries=3`

### 7. 飞书集成范围

**决策**: 核心集成（必须） + 扩展功能（可选）

**核心集成（必须）**:
- 统一登录（OAuth2）
- 组织架构同步（部门、用户）
- 审批集成（CRM提交飞书审批，回调更新CRM）

**扩展功能（可选）**:
- 飞书机器人消息推送（订单状态、审批结果）
- 工作台应用入口
- 日历事件同步

**技术要点**:
- Token使用Redis缓存（过期前5分钟刷新）
- 设置请求速率限制（飞书API限流200 req/min）
- 模块化设计，每个集成点独立可开关

**权衡**:
- 集成越广依赖越强，飞书API变更影响大
- API调用失败需优雅降级，不影响主流程
- 权限token需安全存储（环境变量或密钥管理服务）

**关键行动**:
- [ ] 实现FeishuOAuthBackend统一登录
- [ ] 组织架构同步任务: 飞书webhook → Celery → 更新CRM
- [ ] 审批集成: 创建飞书审批API → 飞书回调处理视图
- [ ] 机器人推送: 封装FeishuBotClient，支持卡片消息
- [ ] Token管理: Redis缓存 + Celery定时刷新
- [ ] 速率限制: 使用Django-ratelimit或自定义装饰器

## 开放风险

1. **租户隔离安全性**: 应用层过滤可能存在绕过风险，需严格代码审查和安全测试
2. **数据同步延迟**: RabbitMQ到飞书的同步可能存在秒级延迟，影响用户体验
3. **LTV计算准确性**: 冷启动启发式评分可能偏差大，需快速迭代优化公式
4. **飞书API变更**: 飞书平台API不稳定性，需建立监控和快速响应机制
5. **历史数据质量**: 导入数据可能存在格式问题或冲突，需充分的清洗和验证流程
6. **运维复杂度**: RabbitMQ、Redis、Celery等多组件增加运维负担，需完善监控和告警
